# 20260729 PDF 文本层/OCR/视觉模型综合对照分析

## 目标

固定抽取 5 张 `20260727报销单` 目录下的 PDF，借用本项目 `OcrService` 实际代码，对比同一批文件在不同路径下导入变量的效果。

这次修正了一个比较口径：项目的 PDF 文本层结果已经经过代码规则适配，不能直接拿它和“裸 OCR/裸大模型”比较。因此新增第 5 项：**直接取 PDF 文本层原文，不使用项目正则适配，由 ChatGPT 评估这段文本被导入变量的成功可能性**。

## 对照路径

1. **PDF 文本层 + 项目服务代码**：`PDFTextStripper` 抽文本，再调用项目 `OcrService.extractInvoiceFieldsFromText` 赋值。
2. **PDF 渲染图 + 本地 OCR 服务 + 项目字段结果**：PDF 第一页渲染成 PNG，调用 `http://localhost:8765/ocr`，记录 OCR 返回文本和 `invoice_fields`。
3. **PDF 渲染图 + ChatGPT 视觉能力**：基于渲染图人工/视觉理解抽取字段。
4. **PDF 渲染图 + Kimi 远程大模型**：项目有 Kimi Provider，但本次没有确认可用且可解密的 Kimi API Key，因此未实际执行。
5. **PDF 文本层原文 + ChatGPT 文本理解评估**：只看 `PDFTextStripper` 原文，不使用项目正则，评估大模型从文本中抽变量的成功可能性。

## 总体结论

这 5 张标准电子发票里，**PDF 文本层并不是不可用，反而是当前最有价值的数据源**。文本顺序确实乱，例如“购/买/方/信息”被拆行、金额合计和开票人位置可能错后，但核心字段本身都在文本里，而且连续关系相对稳定。

项目服务代码经过适配后，5 张样本的核心字段基本都能赋值成功：发票号、日期、购销方、税号、价税合计、税前金额、税额、开票人都能落到变量。

本地 OCR 服务的原始识别 `ocr_raw` 有坐标，潜力更大；但当前导入变量时主要依赖 OCR 服务返回的 `invoice_fields`，导致字段归一结果反而更差。典型问题是 4/5 张把 `buyer_name` 赋成了 `规格型号`，税前金额、税额、开票人大多没有进入标准字段。

ChatGPT 看图和 ChatGPT 看 PDF 文本层原文，理论上都能稳定抽出这 5 张的核心变量。看图更自然；看文本更便宜、更快，也更接近当前双层 PDF 的实际可用信息。

Kimi 远程大模型本次没有跑，不参与准确率排序。

## 当前代码暴露的问题

1. **文本层路径当前效果好，但靠的是已经补过的适配规则。**
   这说明文本层有价值，但也说明纯正则维护成本会继续增长。

2. **本地 OCR 的原始数据没有被充分利用。**
   OCR 返回的 `ocr_raw` 有 `bbox` 坐标，里面能看到买方名称、税前金额、税额、开票人；但标准字段结果没有完整映射。

3. **本地 OCR 字段归一有明显缺陷。**
   `drawer` 没映射到 `issuer`，合计行金额没有补进 `amount_before_tax` / `tax_amount`，部分票据 `buyer_name` 被表头 `规格型号` 覆盖。

4. **第 5 项说明：文本层直接给大模型，可能比直接重新 OCR 更划算。**
   对双层 PDF，先把文本层交给 LLM 做结构化抽取，通常比渲染图片再视觉识别更便宜、更快，也避免 OCR 二次误识别。

## 阶段性建议

不要把策略改成“所有双层 PDF 都重新 OCR”，也不要只靠“字段是否齐全”决定是否继续走下一层。更合适的方向是：**字段值必须带来源区域，先判断值是否来自合理位置**。

短期最值得做的两件事：

1. 对标准电子发票增加区域坐标解析：`buyer_name` 来自购方区，`seller_name` 来自销方区，金额来自合计区/表格金额列，开票人来自底部开票人区。
2. 增加可疑字段复核：字段有值但来源区域不对时，才调用文本大模型或视觉大模型二次判断。

## 补充：ocr_raw.bbox 区域恢复试验

针对“字段齐全但取错，代码很难判断是否继续分流”的问题，又补做了一次区域法试验。

这次不看 OCR 服务返回的 `invoice_fields`，而是直接解析本地 `8765` OCR 服务返回的 `ocr_raw.bbox`。粗略按当前电子发票模板切区域：

- 左上：购方区。
- 右上：销方区。
- 中部：项目明细表格区。
- 下部：合计/价税合计区。
- 底部：开票人区。

批量跑了目录下全部 19 个 PDF，结果文件：

- `bbox-region-analysis.md`

### 区域法结果

| 指标 | 结果 |
|---|---:|
| 批量 OCR 文件数 | 19 |
| 区域法避免 `buyer_name=规格型号` 这类表头误取 | 8 次 |
| 从合计区补出税前金额/税额 | 19 次 |
| 从底部开票人区补出开票人 | 9 次 |

典型例子：机票电子发票里，OCR 服务返回的 `invoice_fields.buyer_name` 是 `规格型号`，但 `ocr_raw.bbox` 里：

```text
购方区：名称：广东维信智联科技有限公司 | 购买方信息 | 统一社会信用代码/纳税人识别号:91441900762909683X
表格区：项目名称 | 单位 | 规格型号 | 数量 | 单价 | ...
```

区域法天然知道 `规格型号` 在表格头区域，不在购方区，所以不会把它赋给 `buyer_name`。

同一张票的合计区也很清楚：

```text
合计区：计 | 合 | ￥1871.70 | ￥112.30 | 价税合计（大写) | 壹仟玖佰捌拾肆圆整 | （小写）￥1984.00
开票人区：开票人：周晶
```

所以区域法能补出：

- `amount_before_tax=1871.70`
- `tax_amount=112.30`
- `total_amount=1984.00`
- `issuer=周晶`

### 这说明什么

你的质疑成立：靠“字段是否齐全”做分流不可靠，因为错值也可能看起来是齐全的。

更靠谱的判断不应该是“字段有没有值”，而应该是“字段来自哪个区域”。例如：

- `buyer_name` 必须来自购方区，不能来自表格头。
- `seller_name` 必须来自销方区。
- `amount_before_tax` 和 `tax_amount` 优先来自合计区或明细表金额列/税额列。
- `issuer` 必须来自底部开票人区。
- 发票号、日期优先来自右上角发票信息区。

区域法的价值不是补漏，而是能做“来源校验”：即使字段有值，也能判断这个值是不是从合理区域来的。

### 局限

区域法对标准电子发票很有效；但对行程单、报销单、货拉拉行程报销单这类非发票模板弱很多，因为它们没有固定的购方/销方/合计区布局。

所以更合理的技术路线不是“四级分流”，而是：

1. **先识别文档类型/版式。**
   标准电子发票、行程单、报销单、保险票、交通平台发票分开处理。

2. **标准电子发票走区域坐标解析。**
   用 `ocr_raw.bbox` 或 PDF 文本坐标按区域恢复字段，并记录每个变量的来源区域。

3. **变量赋值要带来源和置信度。**
   例如 `buyer_name.source_region=buyer_block` 才可信；如果是 `table_header`，即使有值也判为可疑。

4. **只对可疑字段做二次模型判断。**
   不再简单按“字段是否为空”决定是否走下一层。

这比之前说的固定四级分流更靠谱。
