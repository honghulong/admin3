## 背景

本文单独记录 2026-07-29 关于“本地运行 OCR 大模型”与“将 `ocrserver` 改为 PaddleOCR server 版模型”的服务器配置和技术取舍判断。

核心问题：

- 如果本地跑可执行 OCR 的大模型，并希望接近 ChatGPT 的视觉理解和结构化准确度，需要什么服务器配置。
- 如果把现有 `ocrserver` 改成 PaddleOCR server 版模型，能获得什么收益，需要什么服务器配置。

## 1. 本地运行 OCR 大模型

如果目标是接近 ChatGPT 这种“看图理解票面结构、OCR、字段归属判断、纠错、结构化 JSON 输出”的效果，不能只看普通 OCR，需要考虑多模态大模型，也就是 VLM。

大致配置建议：

| 目标 | 推荐配置 |
|---|---|
| 勉强可用，量化模型验证 | 单卡 RTX 4090 24GB，128GB 内存，NVMe SSD |
| 比较靠谱，小并发 | 单卡 RTX 6000 Ada 48GB / L40S 48GB，128-256GB 内存，NVMe SSD |
| 接近线上大模型体验 | 2 张 48GB 级 GPU，或 A100/H100 80GB，256GB 内存 |
| 多用户生产并发 | 多卡 48GB/80GB，单独推理服务，队列限流 |

量化模型可以降低显存占用，但会带来代价：

- 结构化 JSON 稳定性可能下降。
- 小字、印章、表格线、金额位置判断可能变差。
- 中文票据字段纠错能力通常弱于云端大模型。
- 高分辨率 PDF 转图片后，推理速度未必理想。

结论：本地量化 VLM 可以作为验证路线，但如果要求接近 ChatGPT 级别准确度和稳定性，服务器预算不会低。单张 RTX 4090 更适合做可行性验证，不宜直接按稳定生产能力预期。

## 2. ocrserver 使用 PaddleOCR server 版模型

这条路线更现实，也更贴近当前 admin3 已变更后的 `ocr_raw.bbox` 区域解析方案。

PaddleOCR server 版模型主要提升的是 OCR 层能力：

- 文本检测框更稳定。
- 小字识别、密集表格识别通常优于 mobile 模型。
- `ocr_raw.bbox` 坐标质量更好，便于按购方区、销方区、金额区、表格区恢复字段。
- 数据不需要外发，适合本地化部署和内网环境。
- 成本、速度、部署复杂度通常低于本地 VLM。

推荐配置：

| 场景 | 推荐配置 |
|---|---|
| 本地开发 / 低并发 | 8 核 CPU，32GB 内存，可无 GPU，但速度较慢 |
| 稳定服务版 | 16 核 CPU，64GB 内存，RTX 3060/4060Ti 16GB 以上 |
| 比较舒服 | 16-32 核 CPU，128GB 内存，RTX 4090 24GB |
| 小型生产 | 32 核 CPU，128GB 内存，L4 24GB / L40S 48GB |

需要注意：PaddleOCR server 版不是大模型理解能力。它主要做文字检测和文字识别，不会天然知道哪个金额是价税合计、哪个金额是税额、哪个名称属于购买方或销售方。

因此，即使换成 server 版模型，字段结构化仍然要依赖 admin3 当前方案：

- `ocr_raw.bbox` 区域解析。
- 锚点定位。
- 表格区恢复。
- PDF 文本层正则补字段。
- 业务规则校准和兜底。

## 3. 方案建议

当前建议优先级：

1. 优先把 `ocrserver` 升级为 PaddleOCR server 版模型，并继续强化 `ocr_raw.bbox` 区域解析。
2. 保留 PDF 文本正则作为兼容支路，不再把固定正则作为真实用户票据的唯一主方案。
3. 暂不优先投入本地 VLM 生产化，除非业务明确要求数据完全不出本地且预算允许较高 GPU 配置。
4. 本地 VLM 可作为后续实验方向，用少量疑难票据验证它是否能补足 bbox + 规则方案无法覆盖的异常结构。

总体判断：PaddleOCR server 版 + bbox 区域解析，是当前性价比最高、最贴近现有系统改造方向的路线；本地 VLM 更像高成本增强路线，不适合作为第一阶段默认方案。
