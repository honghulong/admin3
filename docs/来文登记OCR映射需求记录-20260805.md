## 1. 背景

来文登记模块需要支持上传扫描件后调用 OCR，并将 OCR 结果辅助填入来文主表字段。当前来文扫描件 OCR 与报销发票 OCR 是两条独立链路：

- 报销发票 OCR 继续使用原报销模块自己的 OCR 服务和解析逻辑。
- 来文登记扫描件 OCR 使用远程 GPU OCR 服务：`http://120.234.136.122:18769/ocr`。
- 当前地址先写死在来文模块中，后续如需多环境切换，应抽为配置项。

远程 OCR 健康检查曾确认：

- 服务：`paddleocr-gpu`
- CUDA：启用
- 模型：`PP-OCRv5_server_det` + `PP-OCRv5_server_rec`

## 2. OCR JSON 结构与原始文件

本次测试扫描件 OCR 原始返回文件保存位置：

`D:\hongmengProjects\admin3\logs\incoming_scan_1_gpu_ocr_response.json`

该 JSON 的有效业务结构主要在：

```text
pages[].lines[]
```

每个 `line` 对象包含：

- `text`：识别文本
- `confidence`：置信度
- `x1/y1/x2/y2`：矩形坐标
- `bbox`：四点坐标
- `page_no` 所在页码由父级 page 提供

样例中可识别出：

- `收文编号`
- `LW20260804-001`
- `收文时间`
- `2026年08月04日`
- `文件标题`
- `关于开展电子公文来文登记系统试运行工作的通知`

## 3. 已发现并修复的问题

### 3.1 页面空白

原因：

后端 `admin3-server` jar 中嵌入的 `admin3-ui` 前端包是旧版本，缺少 `incoming-document-list.*.js` 动态 chunk。

处理：

以后涉及前端资源或无法判断前后端影响范围时，统一使用 reactor 全量构建：

```powershell
D:\hongmengProjects\admin3\mvnw.cmd -pl admin3-server -am -DskipTests clean package
```

不能只执行：

```powershell
D:\hongmengProjects\admin3\mvnw.cmd -pl admin3-server -DskipTests package
```

否则可能继续嵌入旧的 `admin3-ui`。

### 3.2 列表页打开后显示暂无数据

数据库中 `incoming_document` 实际已有数据，但前端显示 0 条。

根因：

后端 `PageDTO` 返回结构是：

```json
{
  "list": [],
  "total": 0
}
```

来文页面错误按 Spring Page 的字段读取：

```ts
res.data.content
res.data.totalElements
```

处理：

已改为：

```ts
tableData.value = res.data.list || [];
pageTotal.value = res.data.total || 0;
```

同时页面首次进入和从 keep-alive 激活回来时，执行默认查询：

- 清空关键字
- 页码回到 1
- 查询已保存来文

### 3.3 保存后看起来没有生效

来文本身保存实际已落库，但外层列表没有按默认条件刷新，用户容易误判为没有保存。

处理：

来文主表保存成功后调用默认查询，回到第 1 页并清空搜索词。

### 3.4 OCR 返回字段展示不清楚

最初右侧 OCR 字段展示只显示 `engine/input/model` 等顶层服务信息，不显示扫描件文字。

根因：

后端 `IncomingDocumentOcrMapper` 对远程 GPU OCR 返回做了普通 flatten，没有优先识别 `pages[].lines[]`。

处理：

已让 `IncomingDocumentOcrMapper` 优先提取 `pages[].lines[]`，结构化成：

```text
line.001 = 文本 | p1 | conf 0.999 | box x1,y1,x2,y2
line.002 = 文本 | p1 | conf 0.998 | box x1,y1,x2,y2
plain_text = 全文
```

前端再把每个值拆成：

- 主文本：用于展示和赋值
- 附属信息：页码、置信度、坐标，仅用于辅助判断

### 3.5 右侧 OCR 面板仍然很窄

原因：

CSS grid 有 3 列，但右侧面板自动落到了中间 `1fr` 窄列，导致即使设置了 460px 宽度也不生效。

处理：

- 左侧来文资料字段固定到第 1 列
- 右侧 OCR 返回字段固定到第 3 列
- 弹窗宽度调整到 `1180px`
- 右侧列宽调整到 `460px`

### 3.6 取消当前连线无效

原因：

原逻辑只根据 `selectedTarget` 删除映射。完成一次连线后 `selectedTarget` 会被清空，因此按钮无法确定要取消哪条线。

处理：

新增 `selectedMapping`：

- 点左侧已有映射字段，可以选中对应连线
- 点右侧文本区域，可以选中对应连线
- 点连线本身，可以选中对应连线
- 点“取消当前连线”，只删除当前选中的一条映射

## 4. 当前映射 UI 设计

字段连线弹窗分为左右两侧：

- 左侧：来文资料字段，例如 `code/title/docNo/secrecyLevel`
- 右侧：OCR 返回字段，来源于 `line.xxx`

右侧每一行拆成两个横向区域：

```text
[line.001 锚点按钮] [OCR text + 页码/置信度/坐标]
```

规则：

- `line.xxx` 是锚点控件。
- 用户从左侧业务字段连到右侧 `line.xxx`，表示该业务字段绑定到这个 OCR line 对象。
- 右侧文本区域只用于辅助人工判断和选中已有连线，不作为真正锚点。
- 连线保存时，业务字段最终写入的是该 line 的 `text`，不会写入 `conf/box` 等附属信息。

## 5. 当前持久化关系

当前保存的核心映射结构是：

```json
[
  {
    "targetField": "title",
    "sourceField": "line.011"
  }
]
```

含义：

- `targetField`：左侧来文主表字段。
- `sourceField`：右侧 OCR 结构化结果中的 line 锚点。

保存位置：

- 表：`ocr_mapping_config`
- 模块名：`incoming-document`
- 当前按用户维度保存。

当前自动赋值方式：

1. 新扫描件 OCR 完成。
2. 后端生成新的 `ocrBusinessJson`，其中包含新的 `line.xxx`。
3. 前端读取已保存映射。
4. 按 `sourceField=line.xxx` 找到对应行。
5. 取该行 `text` 赋给 `targetField`。

## 6. 后续可选映射策略

### 6.1 按 line 序号映射

示例：

```json
{
  "targetField": "title",
  "sourceField": "line.011"
}
```

优点：

- 实现简单。
- 用户能直观看到 `line.xxx`。
- 同一模板、OCR 行序稳定时可快速复用。

风险：

- OCR 行切分、漏识别、合并行、插入噪声行时，`line.011` 可能不再对应同一业务含义。

### 6.2 按坐标区域映射

示例方向：

```json
{
  "targetField": "title",
  "sourceField": "line.011",
  "sourceBox": [258, 422, 948, 456],
  "strategy": "REGION"
}
```

优点：

- 对固定版式表单更稳。
- 即使 OCR line 序号变化，只要文字仍落在相近区域，就能自动取值。

风险：

- 需要处理图片缩放、DPI、页面尺寸变化。
- 需要定义坐标容差和多候选选择规则。

### 6.3 建议演进路线

第一阶段：

- 保留当前 `targetField + sourceField`。
- 完善 UI，让用户能清楚选择 `line.xxx`。
- 验证同模板多张扫描件中 line 序号是否稳定。

第二阶段：

- 保存映射时同时保存 line 对象的坐标。
- 自动赋值时优先按坐标区域匹配。
- 找不到合适区域时回退到 `sourceField=line.xxx`。

第三阶段：

- 支持模板级映射，而不只是用户级映射。
- 映射关系中增加置信度、坐标容差、字段类型和候选排序规则。
