## 1. 背景

来文登记模块需要支持上传扫描件后调用 OCR，并将 OCR 结果辅助填入来文主表字段。当前来文扫描件 OCR 与报销发票 OCR 是两条独立链路：

- 报销发票 OCR 继续使用原报销模块自己的 OCR 服务和解析逻辑。
- 来文登记扫描件 OCR 使用远程 GPU OCR 服务：`http://120.234.136.122:18769/ocr`。
- 当前地址先写死在来文模块中，后续如需多环境切换，应抽为配置项。

远程 OCR 健康检查曾确认：

- 服务：`paddleocr-gpu`
- CUDA：启用
- 模型：`PP-OCRv5_server_det` + `PP-OCRv5_server_rec`

前端再把每个值拆成：

处理：

- 点右侧文本区域，可以选中对应连线
- 点连线本身，可以选中对应连线
- 点“取消当前连线”，只删除当前选中的一条映射

## 4. 当前映射 UI 设计

字段连线弹窗分为左右两侧：

- 左侧：来文资料字段，例如 `code/title/docNo/secrecyLevel`
- 右侧：OCR 返回字段，来源于 `line.xxx`

右侧每一行拆成两个横向区域：

```text
[line.001 锚点按钮] [OCR text + 页码/置信度/坐标]
```

规则：

- `line.xxx` 是锚点控件。
- 用户从左侧业务字段连到右侧 `line.xxx`，表示该业务字段绑定到这个 OCR line 对象。
- 右侧文本区域只用于辅助人工判断和选中已有连线，不作为真正锚点。
- 连线保存时，业务字段最终写入的是该 line 的 `text`，不会写入 `conf/box` 等附属信息。

## 5. 当前持久化关系

当前保存的映射关系不再只把 `cell.xxx` / `line.xxx` 当作唯一依据。`cell.xxx` 和 `line.xxx` 是前端基于当前 OCR JSON 顺序生成的界面锚点，不是 OCR 服务保证稳定的原生 ID，因此只能作为显示名和兜底依据。

### 5.1 多维锚点结构

当前保存的核心映射结构示例：

```json
[
  {
    "targetField": "title",
    "sourceField": "cell.010",
    "sourceType": "table_cell",
    "sourceText": "关于开展电子公文来文登记系统试运行工作的通知",
    "sourceRect": [203, 399, 1025, 528],
    "sourceIndex": 10,
    "spatialAnchor": {
      "labelText": "文件标题",
      "labelField": "cell.009",
      "labelRect": [49, 399, 204, 528],
      "relation": "right-neighbor",
      "sameRow": true,
      "nearest": true
    }
  }
]
```

含义：

- `targetField`：左侧来文主表字段。
- `sourceField`：右侧 OCR 结构化结果中的界面锚点，例如 `cell.010` 或 `line.011`。该编号由前端按当前解析顺序生成，不可单独视为稳定业务锚点。
- `sourceType`：锚点类型，例如 `table_cell`、`ocr_line`、`plain_text` 或兼容旧数据的 `legacy`。
- `sourceText`：建立映射时该锚点的文本，仅用于辅助判断和调试，不作为唯一匹配条件，因为下一张表的真实值可能变化。
- `sourceRect`：建立映射时该锚点的坐标，用于候选排序和兜底判断，但不能单独依赖，原因是扫描件缩放、倾斜、裁切、行高变化都会造成坐标漂移。
- `sourceIndex`：建立映射时该锚点在对应结构中的序号，用于显示和兜底。
- `spatialAnchor`：空间关系锚点。当前优先保存“标签格 + 关系”，例如“`文件标题` 右侧同一行最近的值格”。

保存位置：

- 表：`ocr_mapping_config`
- 模块名：`incoming-document`
- 当前按用户维度保存。

### 5.2 自动赋值优先级

1. 新扫描件 OCR 完成。
2. 前端从当前扫描件 `ocrRawJson` 中生成可选锚点清单，优先使用 `restore.cell_mapping.tables[].cells[]`，其次使用 `pages[].lines[]`，再补充 `plain_text`。
3. 前端读取已保存映射。
4. 若映射中存在 `spatialAnchor`，优先按空间关系取值：
   - 找到文字等于 `labelText` 的标签格；
   - 在同一行内寻找位于标签格右侧的候选值格；
   - 取垂直重叠率满足阈值且距离最近的值格；
   - 将该值格文本写入 `targetField`。
5. 若空间关系匹配失败，再回退到 `sourceField=cell.xxx/line.xxx` 编号取值。
6. 若编号也找不到，不自动赋值，保留用户人工确认空间。

### 5.3 当前已实现的空间关系

当前已实现 `right-neighbor`：

```text
目标值 = 指定标签格右侧 + 同一行 + 最近的表格单元格
```

典型例子：

- `来文单位` -> 右侧最近值格：`广东省数字政务服务中心`
- `密级` -> 右侧最近值格：`普通`
- `文件标题` -> 右侧最近值格：`关于开展电子公文来文登记系统试运行工作的通知`

该规则类似 GIS 中的空间拓扑关系判断，核心不是“第几个 cell”，而是“目标块与标签块之间的位置关系”。

### 5.4 OCR line 邻居查找规则与判定样例

2026-08-11 补充：来文登记的字段映射需要把“规则”和“应用过程”分开理解。

- 规则：用户在连线界面建立并保存的映射 JSON，例如 `targetField/sourceField/sourceRect/lineAnchor/spatialAnchor`。
- 应用过程：某一次 OCR 内容下，系统按当前规则重新解析并写入表单字段的过程。该过程会记录 `mappingRule`、`applyResult`、`reason`、`fallback` 等历史，保存到 `incoming_document.ocr_mapping_apply_history`，用于“赋值历史”tab 只读展示。

当前 `ocr_line` 的 `lineAnchor` 生成规则是“水平邻居”：

1. 用户把业务字段连到某个 OCR 行，系统把该 OCR 行视为目标值行，例如 `sourceField=line.013`。
2. 系统先在目标值左侧找最近的 OCR 行；找不到再在目标值右侧找最近的 OCR 行。
3. “左侧/右侧”不是靠文本阅读顺序判断，而是靠矩形中心点 X 坐标判断：
   - 左邻居：候选行中心点 X 小于目标值中心点 X。
   - 右邻居：候选行中心点 X 大于目标值中心点 X。
4. “同一水平带”不是要求肉眼完全平行，而是要求两个矩形在 Y 轴方向有足够重叠。当前实现使用：
   - `verticalOverlapRatio(candidate.rect, source.rect) > 0.35`
   - 含义：候选行和目标值行的上下范围有超过 35% 的重叠，才认为它们可以构成水平邻居。
5. 多个候选同时满足时，优先选水平间距最近者；间距相同再按矩形中心距离排序。

因此，`lineAnchor` 的“水平邻居”更准确地说是“Y 轴投影有足够重叠的左右邻居”，不是“视觉上完全在一条直线上的邻居”。

找得到邻居的例子：`办公室意见`。

```text
左侧标签块：办公室 / 意见
右侧目标值：请综合科登记后转信息化办提出办理意见。-1
```

从截图看，左侧“办公室/意见”被排成两行，但它整体占据的竖向范围覆盖了右侧长文本所在的水平带。OCR 若把左侧标签识别成一个较高的 `line` 或一个较高的块，它的矩形 Y 范围会和右侧目标值矩形有明显重叠。即使肉眼觉得两边不是严格水平，算法仍可能满足 `verticalOverlapRatio > 0.35`，于是生成类似：

```json
{
  "relation": "right-neighbor",
  "anchorText": "办公室意见",
  "targetText": "请综合科登记后转信息化办提出办理意见。-1"
}
```

找不到邻居的例子：`阅者签字`。

```text
左侧标签块：阅者 / 签字
右侧目标值：王明-1
```

这张截图里，“阅者”和“签字”被拆成上下两行，而“王明-1”位于两行之间偏中的位置。若 OCR 把“阅者”和“签字”分别识别成两个独立 `line`：

- “阅者”的矩形在上方，和“王明-1”的 Y 轴重叠可能不足。
- “签字”的矩形在下方，和“王明-1”的 Y 轴重叠也可能不足。
- 两个标签行合起来肉眼能看懂是“阅者签字”，但当前算法不会自动把多个 OCR line 合并成一个标签块。

所以牵线到 `王明` 时可能只保存：

```json
{
  "targetField": "readerSigner",
  "sourceField": "line.018",
  "sourceText": "王明",
  "sourceRect": [221, 1143, 292, 1186]
}
```

没有 `lineAnchor` 并不表示值不可用，而是表示“生成规则时没有找到满足水平邻居条件的文本锚点”。后续自动赋值仍可能通过 `sourceRect` 的矩形兜底找到正确值，并在历史里显示类似：

```text
matched sourceRect nearest ocr_line -> line.xxx
```

后续扩展方向：

- 水平邻居：继续使用 Y 轴投影重叠判断左右关系。
- 垂直邻居：新增 `above-neighbor` / `below-neighbor`，应使用 X 轴投影重叠判断上下关系。
- 文本块邻居：对“阅者 / 签字”这类被拆成多行的标签，先把近距离、多行、同列文本合并成一个候选标签块，再判断它与目标值的空间关系。
- 赋值历史：每次应用规则时必须保留命中路径，区分 `lineAnchor` 命中、`spatialAnchor` 命中、`sourceRect` 命中和最终 `sourceField` fallback，避免日后只看表单值而无法解释来源。

## 6. 后续可选映射策略

### 6.1 按 line 序号映射

示例：

```json
{
  "targetField": "title",
  "sourceField": "line.011"
}
```

优点：

- 实现简单。
- 用户能直观看到 `line.xxx`。
- 同一模板、OCR 行序稳定时可快速复用。

风险：

- OCR 行切分、漏识别、合并行、插入噪声行时，`line.011` 可能不再对应同一业务含义。
- `cell.xxx` / `line.xxx` 由前端按解析顺序生成，OCR 返回顺序如果变化，单独依赖编号会导致映射错位。

### 6.2 按坐标区域映射

示例方向：

```json
{
  "targetField": "title",
  "sourceField": "line.011",
  "sourceBox": [258, 422, 948, 456],
  "strategy": "REGION"
}
```

优点：

- 对固定版式表单更稳。
- 即使 OCR line 序号变化，只要文字仍落在相近区域，就能自动取值。

风险：

- 需要处理图片缩放、DPI、页面尺寸变化。
- 需要定义坐标容差和多候选选择规则。
- 如果填表内容撑高行高或改变表格局部布局，绝对坐标也可能漂移，因此坐标只适合作为多维锚点中的一项，不能作为唯一依据。

### 6.3 按结构空间关系映射

示例方向：

```json
{
  "targetField": "secrecyLevel",
  "sourceField": "cell.004",
  "sourceType": "table_cell",
  "spatialAnchor": {
    "labelText": "密级",
    "relation": "right-neighbor",
    "sameRow": true,
    "nearest": true
  }
}
```

优点：

- 不依赖 OCR 返回数组顺序稳定。
- 比绝对坐标更能适应整体缩放、轻微偏移和部分行高变化。
- 符合表格类公文“标签格 + 值格”的自然结构。

风险：

- 需要标签文字能够被稳定识别。
- 对“标签下方取值”“跨行大文本区”“多个标签共同限定”等复杂版式，还需要继续扩展关系类型。

### 6.4 建议演进路线

第一阶段：

- 保留 `targetField + sourceField` 作为显示和兜底。
- UI 清楚展示 `cell.xxx` / `line.xxx`、文本、坐标和类型。
- 映射保存时同步记录 `sourceType/sourceText/sourceRect/sourceIndex`。

第二阶段：

- 对表格单元格保存 `spatialAnchor`。
- 自动赋值时优先按“标签格 + 空间关系”匹配。
- 找不到合适空间关系时回退到 `sourceField=cell.xxx/line.xxx`。

第三阶段：

- 支持模板级映射，而不只是用户级映射。
- 扩展更多空间关系：`below-neighbor`、`same-column`、`contains`、`nearest-in-region`、多标签联合约束等。
- 映射关系中增加置信度、坐标容差、字段类型、候选排序规则和低置信度人工确认提示。
