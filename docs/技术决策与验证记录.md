## 2026-08-04：来文登记与扫描件 OCR 智能映射

### 需求目标

在完成报销发票识别阶段后，新增“来文登记”业务模块，用于管理单位收到的公文/来文信息，并支持扫描件附件 OCR 识别后通过字段映射填充来文资料表单。

本轮范围包括：
- 来文主表管理：编号、载体编号、文件标题、来文字号、密级、紧急程度、经办人、备注。
- 基础 CRUD：列表、新增、编辑、删除、详情查看。
- 普通附件管理：上传、预览、删除。
- 扫描件附件作为来文下级明细独立管理：上传、删除、列表展示、OCR 识别。
- OCR 接口由后端转发到 `http://120.234.136.122:18769/ocr`，避免前端跨域。
- OCR 原始 JSON 完整保存，同时过滤响应状态码、通用 message 等系统字段，仅暴露业务字段给映射器。
- 字段映射弹窗支持左侧来文字段、右侧 OCR 字段、点击连线、取消连线、重置、保存并立即赋值。
- 映射配置持久化，作为当前用户默认映射；下一次 OCR 返回后可自动应用到表单。

### 技术决策

| 事项 | 决策 | 原因 |
|---|---|---|
| 模块入口 | 顶级菜单“来文登记” | 与“报销管理”等业务模块并列，不放在“系统管理”下。 |
| 权限模型 | 使用现有 `resource` / `role_resource` | 保持与系统菜单、报销管理、OCR 执行管理一致。 |
| 主表模型 | 新增 `incoming_document` | 独立承载来文业务字段，避免混入报销模型。 |
| 扫描件明细 | 新增 `incoming_scan_attachment` | 扫描件是来文的下级明细，需保存 OCR 状态、原始 JSON 和业务字段 JSON。 |
| 普通附件复用 | `attachment` 增加 `incoming_document_id` | 复用现有附件下载、预览和软删除能力，减少重复模型。 |
| 映射配置 | 新增 `ocr_mapping_config`，按 `module + user_id` 保存 JSON | 支持后续扩展到其他 OCR 映射场景；当前模块名为 `incoming-document`。 |
| OCR 转发 | 后端 `HttpClient` 以 multipart 方式调用 OCR 服务 | 避免前端跨域，并统一保存识别结果。 |
| OCR 字段过滤 | `IncomingDocumentOcrMapper` 展开业务 JSON 叶子节点，跳过 `code/status/success/message/msg/error/requestId/traceId` 等系统字段 | 防止用户把响应状态字段误连到业务表单。 |
| 字段连线 UI | 前端使用 Vue + SVG overlay，不引入 JsPlumb/LeaderLine | 最小依赖、易维护，已满足点击连线、取消、重置、保存应用。 |
| 映射数据结构 | `[{ "targetField": "title", "sourceField": "ocr_title" }]` | 简单、可读、可直接持久化和回放。 |

### 后续注意事项

- 当前 OCR 接口地址固定为 `http://120.234.136.122:18769/ocr`，如需多环境切换，后续应抽到配置项。
- 字段映射当前以用户维度保存；若业务要求全局模板，可在 `ocr_mapping_config.user_id` 为空时作为全局默认模板。
- 当前字段映射 UI 是点击式连线，不支持复杂拖拽曲线编辑；如未来映射器复杂度显著上升，再评估 JsPlumb 等库。
- 扫描件 OCR 自动赋值只改变前端表单值，最终仍以用户点击保存后的来文主表数据为准。
- `cell.xxx` / `line.xxx` 是前端按当前 OCR JSON 解析顺序生成的界面锚点，不是 OCR 服务保证稳定的原生 ID。映射自动赋值应优先使用“标签格 + 空间关系”（例如“密级”右侧同一行最近值格），编号仅作为显示和兜底。

## 2026-07-21：OCR 票据兼容性

### 目标与范围

本轮目标是让报销录入支持典型增值税票据之外的交通、货运和数电票据，并保证金额字段不因 OCR 误判而自动写错。

本轮覆盖：

- 增值税电子普通/专用发票图片与 PDF。
- 电子发票（铁路电子客票）。
- 网约车、出租车、长途客运车票、货运服务电子发票。
- 航空运输电子客票行程单的票种和费用分类。
- OFD/XML 通行费电子发票。

非票面截图、普通收据和无法确认总金额的扫描件不自动生成可信金额；保留 OCR 原文或附件，交由用户补录确认。

### 资料调研

国家税务总局 2024 年第 11 号公告明确数电发票包含铁路电子客票、航空运输电子客票行程单等类别，且基本票面字段含发票号码、开票日期、金额、价税合计等。

铁路客运电子发票公告明确铁路电子客票含发票号码、开票日期、购买方、旅客身份信息、行程信息和票价；发票号码为 20 位。

公开来源：

- [国家税务总局关于推广应用全面数字化电子发票的公告](https://fgk.chinatax.gov.cn/zcfgk/c100012/c5236067/content.html)
- [铁路客运推广使用全面数字化电子发票公告](https://fgk.chinatax.gov.cn/zcfgk/c100012/c5235333/content.html)
- [铁路电子客票票样](https://fgk.chinatax.gov.cn/zcfgk/c100012/c5235333/5235333/files/%E7%94%B5%E5%AD%90%E5%8F%91%E7%A5%A8%EF%BC%88%E9%93%81%E8%B7%AF%E7%94%B5%E5%AD%90%E5%AE%A2%E7%A5%A8%EF%BC%89%E6%A0%B7%E5%BC%8F.doc)

公开铁路票样已下载为 `docs/test-invoices/rail-electronic-ticket-template.doc`，仅作本地开发测试。

### 设计

#### 输入与处理策略

| 文件类型 | 首选处理 | 降级处理 |
|---|---|---|
| XML/OFD | 结构化 XML 字段提取 | OFD 内 XML 的文本提取 |
| 数字化 PDF | PDF 内嵌文本提取 | 首页渲染为 PNG 后调用图片 OCR |
| 图片 | 图片 OCR | 无 |

PDF 只有在内嵌文本中成功取得 `total_amount` 时，才使用文本结果自动写入报销数据。这样可以避免 PDF 表格阅读顺序错乱时，误把单价、税额或明细行金额作为报销总额。

#### 字段映射

报销录入的最小可信字段是：票据号、开票/乘车日期、总金额、票据类型。购买方、销售方、税号和税额为可选补充字段。

铁路电子客票新增识别规则：20 位发票号码、中文日期、`票价`/`应付金额`/`实收金额` 和票种 `电子发票（铁路电子客票）`。

费用分类优先级：出租车、客运车票、航空票据在网约车通用关键词之前匹配，避免将“出租车客运服务”归错为网约车。

| OCR 关键词 | 费用类型 | OA 名称 |
|---|---|---|
| 出租车、的士、taxi | `taxi` | 出租车费 |
| 汽车客运、客运车票、长途客运 | `passenger_transport` | 客运交通费 |
| 航空运输、机票、民航 | `air_travel` | 机票/航空运输费 |
| 高铁、动车、火车、铁路 | `rail` | 高铁/动车/火车费 |

#### 样本驱动分类

分类不直接依赖 OCR 引擎的票种名称，而是先收集并标准化以下特征：票面标题、项目名称、销售方名称、备注、行程关键字和文件名。分类器只消费这份标准化特征文本，并按规则表的优先级给出费用类型。

样本库按“原始附件 + 标注清单”维护。标注清单至少包含：样本来源、文件格式、票据类型、期望票号/日期/总金额、期望费用类型和是否允许自动入账。公开票样可进仓库；真实报销票据仅保留脱敏统计和本地测试路径，不上传到版本库。

当前样本规模不足以训练机器学习模型，因此采用可审计的规则表；当新增票据类别时，先补标注样本和回归用例，再调整规则优先级或关键字，不在报销主流程散落特例。

- 不再将 PDF 原文件直接上传到仅支持图片的 OCR 服务。
- 铁路电子客票可识别 20 位票号、日期、票价和票种。
- 出租车、客运车票、机票不被误归为网约车。
- 无法确认总金额时不自动填入报销金额。
- `OcrServiceTest` 全部通过，后端可打包。

## 2026-07-17：报销归集、凭证与状态流转

### 技术决策

- 费用明细归集键固定为 `同一报销单 + 同费用类型 + 同开票日期`；不使用起点、终点、里程或佐证附件作为归集条件。
- 行程单和订单截图只作为某张发票的佐证。其 OCR 仅更新起点、终点和里程，不触发费用明细重新归集。
- 报销主表的 `amount`、`invoiceTotalAmount` 均以有效发票 `totalAmount` 合计为准；删除发票后必须同步重算关联费用明细和主表汇总。
- OCR 无法确认开票日期时，不参与同日归集；历史已提交或已审核数据不做批量迁移。

相关实现：`OcrService.java` 负责 OCR 后归集，`ReimbursementService.java` 负责附件/凭证关系，`reimbursement-list.vue` 负责前端录入与提示。

### 报销状态机

| 状态 | 允许操作 | 后继状态 |
|---|---|---|
| `draft` | 编辑、上传/删除发票、维护明细、提交、删除 | `pending` 或删除 |
| `pending` | 财务退回、财务通过、职工撤回 | `rejected`、`approved`、`recalled` |
| `rejected` / `recalled` | 编辑、删除、再次提交 | `pending` 或删除 |
| `approved` | 仅归档查看 | 终态 |

提交、退回、再次提交、通过分别写入 `submit`、`reject`、`submit`、`approve` 审批日志。
