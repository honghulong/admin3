## 核心问题
Kettle/Pentaho 转换“各层TO主题层映射”执行失败。日志的关键不是长 Java/JDBC 栈，而是业务错误：

```text
输入的 BLOCK_NODE_ID:117017/117018，
在 DIM_MAPPING_STEP_PROCESS 表中未找到对应步骤，

```

判断：这是流程/节点/映射配置未完整保存导致的元数据缺失，不是单纯 SQL 语法问题。

## 技术小技巧

### 1. 长日志先抓业务错误码
不要先陷入 Kettle/JDBC/Java 栈。优先找：`ERRCODE`、`BLOCK_NODE_ID`、业务提示表名。本次关键就是 `ERRCODE-20005` 和 `DIM_MAPPING_STEP_PROCESS`。

### 2. `BLOCK_NODE_ID` 是配置排查入口
看到 `BLOCK_NODE_ID` 未找到对应步骤，应去工作流/节点配置表或配置页面查节点是否已保存，而不是先改查询 SQL。

### 3. 按节点逐个保存，复跑验证
117017 后又出现 117018，说明一个节点修好后可能暴露下一个缺失节点。节奏应是：补配置 -> 保存 -> 复跑 -> 看下一个 `BLOCK_NODE_ID`。

### 4. 主题层配置不是单点操作
“主题层工作流重新配置”之后，还要检查下方/后续工作流配置。只配置当前映射页可能仍然缺步骤。

### 5. 字段映射先自动匹配
字段多时先用自动匹配，再人工补未匹配字段。这样比逐字段手动连线快得多。

### 6. 平台技术字段降低优先级
平台自增技术字段通常不影响主流程，先保证业务字段、节点和下游步骤保存完整。

### 7. 导入建表可能漏字段/元数据
主题层表虽然是新建的，但如果是导入生成，可能缺字段映射或平台需要的元数据。可尝试手动新增字段，触发平台保存相关配置。

### 8. 先截图，后识别
处理长聊天/长日志时，逐页 OCR 太慢。更高效流程是：快速截图 -> 拼联系表 -> 视觉扫读关键页 -> 最后后台 OCR 归档。
